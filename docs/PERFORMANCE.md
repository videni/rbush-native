# 相同画布输入：原版 JS 与本次 C++ 移植性能对照

这份结果只使用前面已经运行的画布数据生成函数、短线段查询、半径和排除集合，没有改成上游随机矩形 workload。原版 JS 与移植 C++ 读取同一组序列化数值，准备与输入解析不计时。每个输入文件 SHA 已保存，原有候选总数也逐条件核对一致。

## 方法

- 5000/10000/50000/100000 条几何、四种原有分布；额外一个 Drawing 根记录。
- 默认容量9，逐项建树/批量建树分别测试；半径2/8/24点，排除0/50%，每条件240段短线段查询。
- 上游 JS 仅从仓库外 pinned reference 获取；C++ 调用本库原生核心，不是之前的 C R-tree 候选。
- 两端保留相同owner查找、bbox检查和排除过滤；计时前逐query比较完整排序ID。
- 2轮预热+9轮采样，报告240次累计p50；不含Swift/CABI桥接、真实笔画相交、提交、渲染或设备耗时。
- Apple M3 Pro，Node v25.2.1，C++ Release。共享主机上观察到其他Xcode构建，数字仅为本次对照，不是受控空闲机器的尾延迟承诺。

## 对齐证据

16份共享fixture、384个实现/参数条件；每条件240次查询，C++完整ID逐次匹配原版oracle，所有候选总数也与前面的同数据结果一致。两种建树策略都验证，不仅比较命中数量。

原始结果和fixture SHA见 [canvas-comparison.json](performance/canvas-comparison.json)。`logs/canvas-fixtures/` 保存本地实际输入；重新运行 `node benchmarks/compare.mjs` 可生成同值fixture并分别运行两端，原生目标由CMake生成 `rbush_canvas_fixture`。首次运行先执行 `scripts/build-native.sh`。

这说明本次移植在这组候选查询里比原版JS更快，不能据此承诺项目整次擦除、mini map或Swift集成会按相同倍数加速。上游原始bench工作负载保留为库内工具，未混入本报告。
